# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What Reiverr is

Reiverr 2.0 is a TV-first media UI: TMDB discovery plus playback of local media that the built-in requests and torrent downloads put on disk, driven with a remote/d-pad and required to run on old TV browsers (Tizen 5.5, roughly Chromium 69). That target shapes most frontend decisions below. `README.md` is the user-facing doc.

## Workspaces

| Path        | Package            | Role                                                                                          |
| ----------- | ------------------ | --------------------------------------------------------------------------------------------- |
| `frontend/` | `reiverr-frontend` | Svelte **3** + Vite 4 + Tailwind 3 single-page app (no SvelteKit)                             |
| `backend/`  | `reiverr-backend`  | NestJS 12 (ES modules) + MikroORM 7 + SQLite API on port 9494; also serves the built frontend |
| `tizen/`    | -                  | Samsung TV packaging (Docker + `install.sh`); `webos/` is a prebuilt bundle only              |
| `android/`  | -                  | Android TV / Fire TV packaging: a WebView app, built and signed in Docker (`package.sh`)      |

## Commands

Run from the repo root unless noted. Node >= 22.17 (MikroORM 7 and its SQLite driver need it; the Docker images use Node 24).

```sh
npm install                      # installs both workspaces (the Dockerfile does only this)
npm run build                    # backend -> frontend (order matters, see below)
npm run dev:backend              # nest --watch with NODE_ENV=development on :9494
npm run dev                      # vite dev server on :5173
npm run start:prod               # node backend/dist/src/main (pending migrations are applied at boot)
npm run lint                     # frontend: prettier --check + eslint; backend: eslint --fix (it rewrites files)
npm run format                   # prettier --write in both
npm test                         # frontend playwright + backend vitest
npm run generate:backend-openapi # regenerate the frontend API client from backend/swagger-spec.json
npm run build:tizen              # docker build of the Samsung TV app into tizen/Reiverr.wgt, signed with the Tizen SDK's generic developer certificate
npm run deploy:tizen <TV_IP>     # the same, then sdb install; a password after the IP signs with tizen/certificates/author.p12 and distributor.p12
npm run build:android            # docker build of the Android TV app into android/Reiverr.apk, signed with android/keystore
npm run deploy:android <TV_IP>   # the same, then adb install over the network
docker compose -f docker-compose.dev.yml up --build # frontend and backend in containers with live reload
```

Per workspace:

```sh
npm run build -w backend                        # nest build; doubles as the backend type check
npm run check -w frontend                       # svelte-check (frontend type check)
npm run build:here -w frontend                  # build into frontend/dist (what the dev backend serves)
npm run build:tizen -w frontend                 # VITE_PLATFORM=tv build into frontend/dist.tizen

cd backend && npx vitest run src/path/to/file.spec.ts # single unit test (pattern src/**/*.spec.ts)
cd backend && npm run test:e2e                        # test/*.e2e-spec.ts via supertest, on an in-memory database
cd frontend && npx playwright test tests/test.ts
```

Test coverage is thin: the backend has unit specs for pure helpers and for a few services on an in-memory database, `test/downloads.e2e-spec.ts` boots the whole app with a fake torrent engine and a fake Torznab server, and the playwright test targets a page that does not exist. Do not rely on the test commands to validate a change; use the type checks and run the app.

Migrations (run inside `backend/`; the MikroORM CLI loads the TypeScript sources directly through `@oxc-node/core`, no build needed):

```sh
npm run migration:create   # entity diff against src/migrations/.snapshot-reiverr.json -> src/migrations/Migration<timestamp>.ts
npm run migration:up       # apply pending migrations to the dev database
npm run migration:down     # revert the latest migration on the dev database
```

There is no schema synchronization: `main.ts` applies pending migrations at boot in every mode, so after changing an entity run `migration:create`, review the generated file and restart. The scripts set `NODE_ENV=development` so the CLI talks to the dev database; `MIKRO_ORM_DB_NAME=<file>` points the CLI at another file. Commit the snapshot together with the migration.

## Build, serve and environment (easy to trip over)

- `npm run build -w frontend` writes to `backend/dist/dist`, which production `ServeStaticModule` serves. `nest build` has `deleteOutDir: true`, so rebuilding the backend deletes that bundle: build backend before frontend (the root `build` script does).
- In development the backend serves `frontend/dist` instead (`build:here`), and Vite on :5173 is used for live reload. The login form's server URL defaults to `window.location.origin`, so on the Vite server enter `http://localhost:9494` by hand (persisted in localStorage).
- `NODE_ENV` defaults to `production` when unset; only `start:dev` sets `development`. Development mode: uses `backend/config/reiverr.dev.sqlite` (prod: `reiverr.sqlite`; both gitignored), writes `backend/swagger-spec.json` and serves Swagger UI at `/openapi`, and `AuthMiddleware` attaches the user named `test` to any request that has no token.
- `.env` files are not loaded (no dotenv or `@nestjs/config`); export variables in the shell. `JWT_SECRET` signs the tokens (`secret` in development, random per boot when unset in production). Others: `ADMIN_USERNAME`/`ADMIN_PASSWORD` (`UsersService.createOrResetAdmin` at boot: created if missing, an admin's password set back to it when it differs, a non-admin of that name left alone), `TMDB_API_KEY` (has a built-in default), `TMDB_CACHE_TTL` (ms, default 3 days), `DOWNLOADS_DIR` (torrent download directory, default `backend/downloads`, the Docker images set `/data/downloads`; `TORRENT_STREAM_DOWNLOADS` is accepted as a fallback), `TORRENT_PORT` (the port the torrent client listens on for peers, TCP and uTP, validated at boot; unset, a random port), `TORRENT_DHT_PORT` (the UDP port of the DHT node, unset a random one; equal to `TORRENT_PORT` fails the boot, since uTP holds that UDP port and the client would stop), `TORRENT_UPNP` / `TORRENT_NAT_PMP` (`true` lets the client map its ports on the router; default `false`, any other value fails the boot), `TORRENT_WEBRTC` (default `true`; `false` skips WebSocket trackers and so WebRTC peers).
- Docker: the images use `node:24-alpine`; the build stage installs `python3 make g++` because npm compiles `better-sqlite3` when installing from the lockfile. `docker-compose.yml` runs the published image and `docker-compose.override.yml` (applied by default) builds it from the checkout, so `docker compose up --build` is a local production run. `docker-compose.dev.yml` is a separate development environment (`docker compose -f docker-compose.dev.yml up --build`): the `development` Dockerfile stage holds the dependencies, `backend/` and `frontend/` are bind-mounted for live reload (ports 9494 and 5173), and `--renew-anon-volumes` refreshes the containers' `node_modules` after dependency changes. CI runs `docker compose build` and pushes `ghcr.io/aleksilassila/reiverr` (`dev` tag on pushes to `dev`; version tag plus `latest` on `v*` tags). `build-android.yml` builds the Android app when a GitHub release is published (releases are made by hand), signed with the release key from the `ANDROID_KEYSTORE_BASE64` / `ANDROID_KEYSTORE_PASSWORD` secrets, and attaches `Reiverr.apk` to the release; it fails when the tag is not `v` + the root `package.json` version, from which the version code comes. A manual run keeps the APK as an artifact. `build-tizen.yml` attaches `Reiverr.wgt` the same way, without secrets or a tag check: it is signed with the Tizen SDK's generic developer certificate, which newer TVs reject, so users re-sign it with a Samsung certificate made for their TV. The container symlinks `/config` -> `backend/config`. The compose files mount `./data:/data` for the downloads (`/data/downloads`) and the library folders (`/data/tv`, `/data/movies`): both have to be on that one mount for imports to be hard links.

## Git workflow

`master` is the release branch; day-to-day work and pull requests target `dev` (see README). Feature work lives on `feat/*` branches off `dev`. Conventional commit messages (`feat:`, `fix:`, `refactor:`, ...) are the convention.

## Backend architecture

- `main.ts` applies pending migrations and sets global prefix `/api`, CORS and a 50 MB body limit. The database is read from `./config`, relative to the working directory (`backend/`).
- **Auth** (`auth/`): `AuthMiddleware` runs on every route, reads `Authorization: Bearer <jwt>` or `?reiverr_token=` (used in media URLs) and puts the `User` entity on `req.user`; it never rejects. Authorization is per route: `@UseGuards(UserAccessControl)` requires a user and makes a `:userId` param match the caller unless admin, and `@GetAuthUser()` / `@GetAuthToken()` read the request. What belongs to the user of the session is served under `/api/me/...` (`me/user-data`, `me/requests`, `me/storage`, `me/events`), each by a controller of the module that owns it, with the user from `@GetAuthUser()`; there are no routes for acting on another user's data. JWTs are signed with `SECRET` for 365 days. `AuthService.signIn` creates an admin from whatever credentials arrive when no admin exists yet. Passwords are stored as salted scrypt hashes with their parameters (`user.password_hash`, `hashPassword` / `verifyPassword` in `users/password.utils.ts`); a value that is not a hash makes the check throw. Changing one's own password takes the old one; an admin sets the password of another user without it (the profile dialog then hides the field; `test/users.e2e-spec.ts`).
- **Persistence**: MikroORM through `@mikro-orm/nestjs`. `AppModule` imports `MikroOrmModule.forRoot(src/mikro-orm.config.ts)`; feature modules import `MikroOrmModule.forFeature([...])` and services inject `EntityRepository<Entity>` with `@InjectRepository` plus the `EntityManager` from `@mikro-orm/sqlite`. The config lists the entity classes explicitly: folder discovery matches classes by name and `user.entity.ts` also exports a non-entity `Settings` class. Conventions are MikroORM's defaults: snake_case columns, dates stored as epoch milliseconds (compare against numbers in raw SQL, not `date('now')`), uuid ids generated in the entity (`id = randomUUID()`), and no implicit undefined handling (`{ tmdbId: undefined }` means `IS NULL`, TypeORM ignored it). Foreign keys to `User` are `mapToPk` relations named `userId`; the constraint-less joins to the metadata cache are `targetKey: 'tmdbId'` relations with `persist: false`; `LibraryItem.playStates` and `User.mediaSources` are plain properties filled by the services. Simple statements use native operations (`nativeUpdate`, `nativeDelete`, `insert`, query builder upserts), load-modify-save flows use `em.persist(...).flush()`, and reads of large or key-value rows (metadata documents, settings) pass `disableIdentityMap`. Complex reads use the query builder with `sql` fragments (`LibraryService.getMyList`). Entities double as Swagger models via `@ApiProperty`; DTOs are mostly derived with `PickType`/`OmitType`/`PartialType` plus the local `PickAndPartial` helper in `common/common.dto.ts`. Pagination helpers (`@GetPaginationParams()`, `@PaginationApiQuery()`, `@PaginatedApiOkResponse(Dto)`, `PaginatedResponseDto`) live in `common/`.
- **Request context**: the MikroORM module forks the `EntityManager` per HTTP request. Code that runs outside a request needs its own context: `@CreateRequestContext()` (the `LibraryService` boot warm-up), `@EnsureRequestContext()` (`SettingsService`, which plugins call at module init) or `RequestContext.create` (admin creation in `main.ts`). A transaction holds the one SQLite connection (kysely's `ConnectionMutex`) until it ends. Inside `transactional` the injected `EntityManager` and the repositories resolve to the transaction, but a fork, or an `@EnsureRequestContext` / `@CreateRequestContext` method called without a request context (it gets a fork of its own), waits on it forever. `assertOutsideTransaction` (`common/transaction.utils.ts`) fails `MetadataService.getMovieByTmdbId` / `getSeriesByTmdbId` / `findTmdbItems`, the `SettingsService` methods and `ServerLogService.write` (inside one, `writeIn(tx)`) in a transaction's context, as `JobsService.enqueue` fails with an entity manager outside the running transaction.
- **Migrations** (`src/migrations/`): the initial migration creates the schema and, when it finds tables from a TypeORM based release, converts that database in place (tables are renamed aside, copied into the new schema with column and date conversion, then dropped) after copying the file to `<name>.backup-<timestamp>.sqlite` next to it. It accepts any Reiverr 2 schema generation; the metadata cache is only carried over when it has the current layout.
- **Settings** (`settings/`): a `key -> json` table used as a generic KV store (`SettingsService.getValue/saveValue/getOrCreateValue`). `UserSettingsService` stores per-user settings under `user.<id>` (the `User.settings` column is deprecated).
- **Metadata / TMDB** (`metadata/`): `MetadataService` caches full TMDB movie/series documents (with `append_to_response` extras and every season) in `movie_metadata` / `series_metadata`, refreshing when older than `TMDB_CACHE_TTL` or once a release / next-episode date has passed, one fetch per title at a time (`SingleFlight`, in memory: callers that find the row missing or stale join the fetch in progress; a stale row is served at once unless `eager`). Library, requests, local media, indexers and downloads all read through it, and `LibraryService` warms it for every library torrent item at boot. `getEpisodeCounts(em, tmdbId)`, `findCachedMovie(em, tmdbId)` and `findCachedSeries` are cache-only reads that take the caller's entity manager, for reads inside a transaction, where the fetchers fail. `TmdbController` proxies `/api/tmdb/v3/proxy/*` for the frontend with an in-memory cache and short-circuits `/3/movie/:id` and `/3/tv/:id` to the SQLite cache; the `TMDB_API` provider wraps the generated client in a 20 req/s limiter with 429 retries. `tmdb.v3.openapi.ts` is generated by swagger-typescript-api (the `generate:tmdb-openapi` script's output path is stale, check it before running); `tmdb.v3.generated.dto.ts` is an AI-written Swagger-decorated mirror of those types and is maintained by hand.
- **User data** (`user-data/`): `TitleState` (table `title_state`: what a user has with a title, one row per user, media type and TMDB id, made when the user lists the title or plays something of it: `addedToMyListAt` (the my list, null when not on it), `lastPlayedAt`, and the stamped next episode `nextSeason` / `nextEpisode` / `nextAirDate`, the first unwatched episode after the one watched last, in watch order, or the movie itself at 0/0 while unwatched, null when nothing is left; `TitleStateService.stamp` writes it in the transaction where a watched flag changes and when the title is listed, `stampAll` over every row at boot and every night from the refreshed documents) and `PlayState` (progress + watched per movie/episode) keyed by user, media type and TMDB id (movies and series share TMDB ids, so every lookup carries the type). A play state has `watchedAt`, and `PlayStatesService` has `RequestsService.reconcileRequests` reconcile the requests of the user and series when something becomes watched or unwatched (not on progress reports), and `TitleStateService.stamp` the next episode. The catalog module lists the my list from the stamp (`plans/2026-11-01-my-list-page.md`). The module is flat (no sub-folders), with one `UserDataController` under `/api/me/user-data`, as the requests routes: `GET movies/:tmdbId` and `series/:tmdbId` (the document: `inMyList` and the play states), `PUT`/`DELETE .../play-state` (a movie; an episode under `series/:tmdbId/play-states/seasons/:s/episodes/:e`, the whole series `PUT series/:tmdbId/play-states`) and `PUT`/`DELETE .../my-list`.
- **Requests** (`requests/`, entities `MediaRequest` (table `request`), `RequestRule` (`request_rule`) and `RequestSource` (`request_source`)): what a user wants on disk, one row per movie or episode, and the gates a request passes before the library acts on it. The row says nothing of how it is fulfilled: `approved` (every request is approved at creation, as there is no approval; the column and the gates stay for now) and `neededSince` (set once when the request passes the download-ahead gate of the rule of its user with a source, never cleared). A request is **active** when it is approved, needed and has a source. `RequestsService.reconcileRequests(tx, pair)` brings the requests of a (user, title) pair in line with its play states, rule and sources (the requests to delete, the requests that pass the gate, written out in the method), and every writer of requests, rules or play states calls it in its transaction; `reconcileAllRequests` runs it over every pair, each in its own transaction, at 03:50 and at boot. Every change of a request, or of its source, enqueues `library.reconcileBinding {requestId}` in the same transaction (the needed and deleted ones in `reconcileRequests`, the requests in scope of a changed source, the requests of a deleted user). The rule row (one per user, media type and title) holds the limits (`keepNext`, `keepWatched`, `keepWatchedHours`, null is off) and exists while it has one. The source rows (one per user, title, season and episode: episode 0 for a season's, 0/0 for a movie's) say where the requests of their target get their files: `kind` `torrent` with the release as it was picked (`infoHash`, `title`, `indexer`, `size`, `magnetUrl` and the fetched `torrentFile`, lazy), or `file` with `mediaFileId`. `requests.utils.ts`: `resolvedOf(row)` is what a row gives its requests (`ResolvedSource`: the `SelectedRelease` with `forEpisode`, or the file; nothing while a torrent row has no release, which nothing writes yet: the loading state of a future resolve job or quality profile), `sourceOf(rows, season, episode)` the source of an episode: its own, else its season's, `writeSource(tx, row)` replaces the row of a target. `RequestSourcesService` holds what a user does to the rows (`selectRelease`, `selectFile`, `clearSelection`), called by the controller only, on top of `RequestsService`, which knows nothing of it. Selecting a release resolves it through indexers (a link that leads nowhere fails here) and writes the row with the magnet link or the fetched `.torrent` in place of the row the target had, which the library hands to downloads; nothing resolves later. `readRequestWithSource(em, id)` (the row with its source, the `.torrent` included), `findRequests(em, { userId? })` (every request or a user's, with the gate fields, in user, title and episode order), `findRequestsWithSources(em, pair)` (the requests of a title with their sources, without the `.torrent` files, for the status) and `deleteRequests` are what the library calls; `requestFiles(userId, files)` creates a user's requests for the episodes of files with the files as their sources, for the server page. `describeSeriesRequests` / `describeMovieRequests` build the document of a title page (`SeriesRequestsDto`: the requests (`MediaRequestDto`, with the derived `ahead`, as wherever a request is served), the rule and the sources (`EpisodeRequestSourceDto`) with the selected release as picked (`SelectedReleaseDto`) or the selected file's id; `MovieRequestsDto`), served by `GET /api/me/requests/series/:tmdbId` and `movies/:tmdbId`; there are no separate rule reads. `reconcileRequests` emits the `requests` event to the user for the pair whatever it changed, with or without requests of the title (every writer of a pair applies the rule, deleting included). Routes under `/api/me/requests`. The module imports nothing from downloads or the library. Described in `plans/2026-10-21-library-hub.md` and `plans/2026-11-04-request-sources.md`.
- **Downloads** (`downloads/`, entities `Torrent` (keyed by `infoHash`) and `TorrentItem` (`torrent_item`)): downloads what is wanted of torrents and seeds them up to the seed ratio, and knows nothing of requests or the library. The library calls `getOrCreateTorrent(em, release)` (the row at once, idle; a failed torrent gets another go), `requestTorrentItem(em, infoHash, torrent item)` (a claim on the torrent for an episode or a movie, with `onlyVideo` for a torrent picked for the episode itself; a released torrent item is wanted again from the start) and `releaseTorrentItem(em, id)`, and reads `findTorrentItems`, `describeTorrents` and `getTorrentItemFile`. One job, `downloads.reconcileTorrent {infoHash}`: stores the file list once the engine knows it, matches wanted torrent items to files (`torrent-match.ts`: the file named after the episode, the only video of a torrent picked for the episode, the largest video for a movie), stamps `completedAt` when the engine reports a file complete and enqueues `library.importTorrentItem` for every complete torrent item, then decides whether the torrent starts, waits, runs, stops (nothing to download, a torrent item waits for its import), fails, or releases its data (nothing wanted and seeding done), and does it through `TorrentRuntime` (the adapter around the `TorrentEngine` / `TorrentHandle` interface, `TORRENT_ENGINE` token, whose callbacks only enqueue the reconcile). The engine is webtorrent 3 in the API process (`webtorrent.engine.ts`): one client for every torrent (one port, one DHT node), created with the first torrent and again after it stops on an error, WebRTC on unless `TORRENT_WEBRTC=false` (`tracker: { wrtc: false }`); `setWantedFiles` clears the selection and selects the wanted files again, since deselecting a file would also deselect the piece it shares with the next one. It is untyped: `@types/webtorrent` brings `@types/parse-torrent` 11, which would type the indexers' parse-torrent 4 import. Decision and open torrent items in `plans/2026-10-27-torrent-engine-alternatives.md`. A failed torrent stays failed until the library gets it or wants a torrent item of it again; there are no retries. Rows are never deleted by a reconcile; torrents without torrent items and without data go every night. Data lives under `DOWNLOADS_DIR/<info hash>`. `describeTorrents()` (admin, `GET /api/downloads/torrents`) and `describeTitleTorrents(title)` (`GET /api/downloads/series/:tmdbId` and `movies/:tmdbId`, any user: the torrents something of the title is or was wanted from, with the torrent items of the title) are the live views with the engine's snapshots, which the title pages poll while a torrent runs. The reconcile emits the `downloads` event for the titles of the torrent's torrent items. Admin routes: the settings (`seedRatio`). Described in `plans/2026-10-21-library-hub.md`.
- **Indexers** (`indexers/`): server-level Torznab indexers (Jackett, Prowlarr) stored in the settings KV under `indexers`, a Torznab client with caps-based id search and text fallback, release title parsing after Sonarr, and `GET /api/indexers/search/series/:tmdbId?season&episode` returning releases merged by info hash. Search results are cached in memory for an hour and referred to by id, because download links carry the indexer API key. `resolveTorrent` turns a release into an info hash with a magnet link or the fetched `.torrent` when it is selected.
- **Jobs** (`jobs/`): the queue table and `JobsService`: modules `define(type, { concurrency, retry, run })` at init, callers `enqueue(em, type, payload, { runAt })` in their transaction with the dedupe and lock keys of `job-types.ts` (the one vocabulary of what can run with what; a type is named `<module>.<verbObject>` after the module that runs it and its handler, as `downloads.reconcileTorrent`; a job another module enqueues in the transaction of a change is how modules tell each other what happened, as requests enqueuing `library.reconcileBinding`), `main.ts` starts the loop after `listen`, failures retry with a backoff, `drain()` and `pause()` serve tests, admin routes under `/api/server/jobs`. The jobs table is how the modules talk to each other; there are no in-memory events between modules. The runner wraps every job in `EventsService.run`, so the client events a job emits go out when it is done.
- **Events** (`events/`): what the server tells the connected clients so that they fetch again what changed without them, over `GET /api/me/events` (server-sent events, `@Sse`, the token in `reiverr_token`, a keepalive comment every 30 s). `EventsService.emit(event)` is called where a change is written (`client-event.ts`: `requests` and `storage` to one user, `library` and `downloads` to everyone, the title `{ mediaType, tmdbId }` as the data); the event goes out when the unit of work that wrote it is done, after its transactions committed: the HTTP request (`EventsMiddleware`, flushed when the response closes), the job (the runner) or a run wrapped in `events.run` (`reconcileAllRequests`); outside a unit it goes out at once. Deferred to the unit rather than to the commit of a transaction: MikroORM fires `afterTransactionCommit` for savepoints too, and the end of the unit holds whatever the driver does (kysely's mutex in front of the SQLite connection would make a refetch wait for the commit anyway) and causes no refetch for a transaction that rolls back. A notification of the clients of this process only, not how modules talk to each other. The frontend's `lib/queries/events.ts` maps the events to query keys and invalidates, coalescing a burst, and invalidates everything after a reconnect.
- **Server** (`server/`): the admin API of the server page, `/api/server`, a thin `ServerService` over the other services. `GET library?folder=` lists everything in a library folder as a flat list (`LibraryService.getLibraryEntries`: hidden entries included, symbolic links listed and not followed, indexed files with `mediaFileId`, `managed` and the number of requests they fulfil). `GET`/`POST library/scan` preview and run a scan of a library folder (`ScanService.previewScan` and `scanFolder`; `plans/2026-10-06-library-scan.md`). `POST library/delete` deletes entries of a folder (`DeletionService.deleteLibraryEntries` in the library): the entries, a directory with everything in it, and the requests that refer to the deleted files, so that nothing downloads them again. `POST library/request` requests the episodes of the indexed files of entries for the admin, bound to the files (`LibraryService.findLibraryEntryFiles`, `RequestsService.requestFiles`); `POST library/manage` and `POST library/unmanage` mark them managed or external (`LibraryService.setLibraryEntriesManaged`). Described in `plans/2026-10-05-server-files.md`.
- **Storage** (`library/storage.service.ts`, in the library): what the requests of users take, and the gate on capacity. `user.quota_bytes` (null is no quota) is set by admins through `PUT /api/users/:id` with `quotaBytes`, and `UsersService.update` enqueues the sweep when it changes. The library reads the quota through `UsersService.getQuota(em, userId)`, never the table (`LibraryModule` imports `UsersModule`). `StorageService.fitsQuota(em, request, bytes)` says whether bytes more fit the quota of the request's user, by the usage of their requests (held bytes, the distinct files the user's requests hold, managed or external, by `media_file.size`, plus pending bytes, `request_binding.pending_bytes`, the expected size stamped when a download is started; a file held by several users counts for each; there is no running total), without the binding of that request. The fulfilment asks in its transaction when a request is to get a file or a download, which is expected to take `expectedBytes(release.size, forEpisode, episodesInSeason)` (`library.utils.ts`; the season's episode count from `MetadataService.getEpisodeCounts(em, tmdbId)`), and a download starts only while no disk is at the limit; the quota is asked first. The library setting `maxDiskUsagePercent` (null is off) is measured with `statfs` over `DOWNLOADS_DIR` and the library folders (`isDiskFull()`, read and measured before the reconcile's transaction, since the settings are read outside it; a path that cannot be measured is left out; the percent is of used plus available bytes, leaving out the blocks reserved for root). Route: `GET /api/me/storage` (`describeUser(userId)`, `UserStorageController`); the titles on disk with what the user's requests hold of them are the catalog's (`GET /api/catalog/on-disk`, `CatalogService.findOnDisk`, for the downloads page). Described in `plans/2026-10-22-quotas.md`.
- **Upkeep** (`app.service.ts`, `AppService`): everything that runs at boot and every night, in the order it runs, as thin triggers; the work stays in the modules. At boot: reconcile all requests, sweep, have every torrent decide again, stamp the next episodes (not awaited). Nightly, two crons running their steps one after the other (a step that fails is logged and does not stop the rest): 03:50 reconcile all requests and sweep; 04:00 cleanup, scans, the purges of jobs, the server log and unused torrents, then the stamps, last because they refresh documents. The 10 minutes between them are for the reconcile jobs of the deleted requests to let go of their files before the cleanup reads what is held. A new cron or boot task goes there. `TorrentRuntime`'s flush timer and shutdown, the `onModuleInit` job definitions and `JobsService.start()` in `main.ts` stay where they are.
- **Server log** (`server-log/`, table `log_entry`): a persisted record of things the server did on its own, `ServerLogService.write(type, message, data)`, which also prints the message. Written for every file the server deletes: a library file (`file.deleted`, in `DeletionService`) and the downloaded data of a torrent (`download.deleted`, in `DownloadsService.release`). Entries are purged every day at 04:00 server time (`purge`, a `@nestjs/schedule` cron job) by the `server-log` setting: `maxAgeDays` (default 30) and `maxEntries` (default 0), 0 turning a limit off. Admin routes `GET /api/server-log/entries` (paginated, newest first; the Logs tab of the server page lists them) and `GET`/`PUT /api/server-log/settings` (no UI yet). The folder is not called `logs` because `backend/.gitignore` ignores every folder of that name.
- **Library** (`library/`, entities `MediaFile` and `RequestBinding` (`request_binding`); was `local-media`): the hub of the three. It owns the index of the files on disk, the streaming, and how requests are fulfilled, and depends on requests and downloads. `FulfilmentService` defines `library.reconcileBinding {requestId}`, retried with the runner's backoff: in one transaction it reads the request with its source (requests), its binding and what the binding refers to, and brings the binding in line: a request that is gone or not active lets go of the torrent item it waited for (released when no other binding refers to it) and keeps the file it has, unless the library forgot it; a file source binds the file when it is in the library and of the episode, else records the error on the binding; a torrent source keeps a bound file from that torrent (or any bound file, when the torrent was picked for the season), else binds the library's version from that torrent, else ensures the torrent from the selected release, requests the torrent item and binds it. What a request keeps (its file, or the torrent item of its source) passes no gate; what it is to get (a selected file, a version, a download) it gets when it fits (`StorageService.fitsQuota`, and for a download `isDiskFull`, measured before the transaction), else it lets go of what it had and its binding says so: `error` `over-quota` or `disk-full` with no file and no torrent item. `library.importTorrentItem {infoHash, torrentItemId}` (defined by `ImportService`, locked on the torrent, retried with the runner's backoff) places a complete torrent item in the library once (hard link, else copy, as `Name - S01E02 - <8 characters of the hash>.mkv`) and hands it to the fulfilment: `torrentItemImported` gives the file to every binding of the torrent item and releases the torrent item, `torrentItemImportFailed` keeps the failure on the bindings, and the torrent's next reconcile enqueues the import again. `library.sweepRequests {}` (dedupe key `library.sweepRequests`, lock `library`) enqueues the reconcile of every active request bound to nothing, in user, title and episode order, and of every binding whose request is gone: at boot, at 03:50, and whenever room may have been made. Fulfilment enqueues it itself (the private `sweepLater`) when a binding lets go of a file or a torrent item or an import settles what a request takes; the other services and modules enqueue the job directly when they delete files or the data of a torrent, or set a quota or the disk limit. Fulfilment is the only writer of `request_binding`. A request holds its file through its binding: `countByMediaFile` serves the server page, and `DeletionService` deletes the managed files no binding holds at the cleanup (04:00 cron: queues a `library.cleanUpTitle` per title with managed files on the days of the `cleanup` setting; the scans of every folder are queued by the scan service's cron of the same hour, and the cleanup does not wait for them), and what an admin selects together with the requests that have the files. `LibraryService` is the index: the settings (KV key `library`: `movieFolders`, `seriesFolders`, the `cleanup` schedule, `maxDiskUsagePercent`; `cleanup.utils.ts` has the day and next-run helpers), the mount guard (`readAvailableLibraryFolder`), `getTitleMatch` and `findTitleFolders`, the index rows (`findFile*`, `upsertFiles`, `forgetFiles`) and the entries of a folder for the server page. Forgetting files calls `FulfilmentService.filesForgotten(tx, files)` in the deleting transaction (the index reads no binding): the bindings let go of the files, which runs the sweep, and the reconcile of their requests is enqueued, so that they download the files again; a bound file thus always has its row, and the reconcile's check of it is defensive. The settings key, defaults and `readLibrarySettings(settingsService)` are in `library-settings.ts`, read by the index and by `StorageService`, which takes `SettingsService` so that the index can depend on the fulfilment without a cycle. `ScanService` runs the scans (`library.scanTitle`, `library.scanFolder`, `previewScan`, `requestScan` for a title that is looked at, and the nightly cron); `PlaybackService` serves the file listings of the title pages, the stream path and the subtitles. The helpers over the disk are in `disk.utils.ts`, `coversEpisode` (whether a file is of an episode) in `library.utils.ts`. `StatusService.describeTitleStatus(pair)` serves `GET /api/library/series/:tmdbId/status` and `describeMovieStatus(userId, tmdbId)` `movies/:tmdbId/status`: what only the library knows, from rows. `fulfilments` (`fulfilment` for a movie, `FulfilmentStatusDto`) has an entry per request with a binding (`fulfilled` with `mediaFileId`, `failed` with `error` and `errorMessage`, `downloading`; a binding always has a file, a torrent item or an error, `writeBinding` deletes an empty one) and `pending` per active request without one, which the reconcile has yet to look at; a request that is not active and holds nothing has none, as the requests of the title say why (`approved`, `ahead`, the sources). `files` is the index rows of the title (`MediaFileDto`), with `cleanupAt` on a managed file no request of anyone holds. Nothing of the engine or of the torrent item's status, which the client has from the torrents route of downloads, and the clients are told through the `library` event (every `writeBinding` with the title, the index writes, the import, the deletions) when a row changes. Routes under `/api/library` (settings, file lists, `files/:id/stream`, `files/:id/subtitles/:fileName`) and `/api/me/storage`. Described in `plans/2026-10-21-library-hub.md`; the scan is in `plans/2026-10-06-library-scan.md`.

## Glossary

The words the requests, downloads and local media code use, in the sense the code gives them.

- **Title**: a movie or a series, as TMDB knows it: `MediaType` (`movie`, `series`) plus `tmdbId`. The requests, the rules, the play states, the files and the jobs of a title are keyed by it; a row of an episode carries the type of its series with its season and episode, a movie's is at season 0, episode 0.
- **Pair**: a user and a title (`{ userId, mediaType, tmdbId }`). A rule is applied to its pair whole, since it looks at all the requests of its user for the title.
- **Request**: a row saying a user wants an episode (or a movie) on disk. A row that exists is a wish for its file; there are no inactive requests. `approved` is set at creation, as there is no approval; **waiting** is what the clients show of a request without it, which nothing creates any more. The row says nothing of how it is fulfilled: that is the library's **binding**.
- **Rule**: the row of a pair holding the limits. The **keep settings** are `keepWatched` and `keepWatchedHours`, which go by the play states: a watched request they do not retain is deleted. **Download ahead** is `keepNext`.
- **Needed**: a request that passed the download-ahead gate of the rule of its user with a source (`neededSince` set once, never cleared). **Active** is approved, needed and with a source: what the library acts on. **Ahead** is an approved request with a source that is not needed yet: the download-ahead window holds it back (`isAhead`, `ahead` on `MediaRequestDto`).
- **Quota**: `user.quota_bytes`, the most that what a user's requests hold and wait for may take; null is none. **Usage** is held bytes (the distinct files the user's requests hold, by their rows) plus pending bytes (`request_binding.pending_bytes`, the **expected size** of a download, stamped when it is started: the release size, divided by the season's episode count for a season torrent, and replaced by the file's size at the import). A request **fits** when the usage of the user's other requests plus what it is to get is within the quota, and a download only while no disk is at the **disk limit** (`maxDiskUsagePercent` of the library settings, measured with statfs). **Held back** is an active request that did not fit: its binding has only the error `over-quota` or `disk-full`, as of its last reconcile, and it is looked at again by the **sweep** (`library.sweepRequests`, run at boot, at night, and whenever room may have been made). Limits are soft: nothing is taken back for being over.
- **Last watched episode**: the furthest episode, in season and episode order, whose play state is watched. The download-ahead window counts requests from there; an episode in progress is not watched.
- **Source**: the release a user picked for a season or an episode, or the file in the library they picked for an episode or a movie: a row of `request_source`, one per user, title, season and episode (`RequestSourceDto` for the clients). **Selecting** a release or a file writes the row (`selectRelease`, `selectFile`), and `clearSelection` deletes it. An episode's own source wins over its season's. **Selected release**: the release as it was picked, kept on the torrent source row with its magnet link or `.torrent` (`SelectedRelease` in `requests.utils.ts`, `SelectedReleaseDto` for the clients). A **resolved source** (`ResolvedSource`) is what a row gives the requests of its target: the release with `forEpisode`, or the file; a torrent row without its release gives none.
- **Release**: an indexer search result (`Release`, an in-memory object with a short-lived id); not to be confused with **releasing** a torrent, which is stopping it, deleting its data and forgetting its row when nothing refers to it.
- **Resolve**: turning a release into an info hash with a magnet link or a fetched `.torrent` (`IndexersService.resolveTorrent`), at selection only.
- **Torrent**: a row per torrent the server knows, keyed by info hash, created by the library from a selected release when a request needs it (`getOrCreateTorrent`). Its rows stay; its data goes when nothing is wanted and seeding is done.
- **Binding**: the library's row per request (`request_binding`): the **torrent item** the request waits for, or the file it has, and the error that keeps it from its file (`error`, the reason as `FulfilmentError`; `errorMessage`, the text to show). **Reconciling a binding** (`library.reconcileBinding`) brings the binding in line with the request and its source. A request **holds** its file through its binding.
- **Torrent item**: a claim on a torrent for one episode or movie (`torrent_item`, unique per torrent and torrent item), asked for and released by the library, matched to a file of the torrent by downloads (`fileIndex`), **complete** when the engine has the file (`completedAt`), **released** when the library imported it or lets it go (`releasedAt`). A torrent's data stays while a torrent item is wanted.
- **Wanted**: the torrent items of a torrent that are not released. A torrent is **needed** while a wanted torrent item waits for its file or for the file list.
- **Media file**: a row of the index of the library (`media_file`), one per file on disk, with the id the API serves it by. **Managed** means the server may delete it when no request holds it: imported from a torrent (it carries the `infoHash`) or marked so by an admin; the cleanup may delete it. An **external** (unmanaged) row was found on disk and is never deleted or counted.
- **Version**: a managed file of an episode named after its torrent (`... - <8 characters of the hash>.mkv`, the Jellyfin naming). Several torrents give several versions of one episode.
- **Import**: placing the complete file of a torrent item in the library (hard link, else copy), indexing it and giving it to every binding of the torrent item (`library.importTorrentItem`), then releasing the torrent item.
- **Scan**: bringing the rows of one title (`library.scanTitle`) or of a whole library folder (`library.scanFolder`) in line with the disk. **Forgetting** a file is deleting its row and reconciling the requests that had it, whose bindings then let go of it.
- **Not mounted**: a library folder that cannot be read, or is empty while files are indexed in it. Lookups, imports and deletions then fail with 503 instead of touching rows or the mount point.
- **Cleanup**: the nightly deletion of managed files no binding holds (the cron queues a `library.cleanUpTitle` per title), on the days of the `cleanup` schedule of the library settings.
- **Reconcile**: reading rows and making the world match them. As jobs: `library.reconcileBinding` for one request's binding, `downloads.reconcileTorrent` for one torrent (matching, completions, imports, and starting, stopping or releasing it). `RequestsService.reconcileRequests` does it for the requests of a pair, in the caller's transaction: it writes what the play states, the rule and the sources make of them (deletions, needed), then enqueues the reconcile of the bindings of the requests that changed.
- **Job keys**: the **dedupe** key merges an enqueue into a queued job of the same key; the **lock** key keeps jobs of the same key from running at once (`jobs/job-types.ts`). The dedupe key is the type and the payload; the lock key is the resource the job acts on, `request:<id>`, `torrent:<hash>` (shared by the reconcile and the import), `title:<type>:<id>`, `folder:<path>` or `library`.
- **Runtime snapshot**: the live state of a torrent in the engine (`TorrentRuntime.snapshot`: ready, progress, error, files), as opposed to the release snapshot above. The library's status goes by rows alone; the live state reaches the client through the torrents route of a title.
- **Client event**: what the server tells the connected clients over `/api/me/events` so that they fetch again what changed without them (`requests`, `library`, `downloads`, `storage`), emitted where a change is written and sent when the request, job or run that wrote it is done. Not a module talking to a module.
- **Seeding**: a torrent that keeps running after nothing is wanted from it, until `seedRatio` is reached; a seeding torrent is not released even when unreferenced.
- **Play state**: progress and watched flag of a user per movie or episode (`watchedAt` set when it becomes watched). Changing the watched flag is what reconciles the requests; progress is not.
- **Title state**: the row of a user and a title (`title_state`): whether it is on their list and since when, when they last played it, and the **next episode**, the first unwatched episode after the one watched last, in watch order (season 1 on; the movie itself at season 0, episode 0 while unwatched; null when nothing is left), stamped with its air date. **Unwatched** is a stamped episode that has aired, **watched** the rest; **available** is a file of the next episode, or, with nothing aired left, of anything of the title. The my list page filters by these.

## Code style and best practices

- To keep complexity of the codebase down, prefer implementations that fail early when applicable. Recovering is problematic when it introduces a new state that needs special handling elsewhere, thus adding complexity.
- Prefer systems and functions that can be understood locally, in isolation (local thinking). Avoid global shared state that promotes unpredictable, complex behavior.
- Follow the existing code style in the codebase. This should include comments, which are rare in the codebase and should only be included when the code itself cannot be made self describing or when functions get long and difficult to understand at a glance. When commenting data types, consider JSDOC @examples if the datatype benefits from it.

## Use accurate terms, don't abbreviate project vocabulary

- quality profile is not just "profile", instead "quality profile" or QualityProfile as in the code
- torrent item is not just "item", but "torrent item" or TorrentItem
- Longer variable names are ok if they increase readability.
- etc.
